# 共通コード制約

## 目的・適用範囲

この文書を、リポジトリ内のコード実装へ継続的に適用する共通コード制約の正本とする。

実装方針の議論、新規コード、既存コード変更、リファクタリング、コードを含むPull Requestレビューでは、この文書を参照する。

特定RM・特定タスクだけに必要な制約は各タスク側で扱い、共通制約本文を各タスクへコピーしない。

行数やファイル数など、成果に直接つながらない機械的な上限は設けない。

コードが型として正しく動作するだけでなく、人間とAIのどちらが読んでも、意図、役割、変更可能性、境界をできるだけ同じように読み取れる表現を優先する。短さや高度な構文より、後続の実装で誤解されにくいことを優先する。

## 1. 型とデータ境界

- TypeScriptでは`strict: true`を使用する。
- `any`、`as any`、`@ts-ignore`などで型エラーを安易に回避しない。
- 型エラー回避だけを目的とした`@ts-expect-error`を使用しない。
- non-null assertionの`!`を安易に使用しない。
- 外部ライブラリとの境界で型情報が不足する場合は、`unknown`やライブラリ提供型から必要な値を検証し、必要最小限の型変換を行う。
- optionalは、本当に存在しなくても成立する値だけに使用する。
- 「まだ値がない」状態は`null`など一つの表現に統一する。
- 空文字や適当なdefault値で、欠損や異常を正常値に見せない。
- 型推論だけでは契約が曖昧になるstateや境界では型を明示する。
- 外部ライブラリ固有の内部表現を、アプリケーションのstateやドメイン処理へ直接持ち込まない。

### 型表現の使い分け

- 変数や公開値を後続コードでどの型として扱わせるかという契約を示したい場合は、型注釈を優先する。例えば、変更不可の固定配列は`const FIXED_EMOTION_LOGS: readonly FixedEmotionLog[] = [...]`のように表す。
- 推論された具体的な型を保持したまま、値が期待する構造を満たすことだけを検査したい場合に`satisfies`を使用する。
- 値を変更不可として扱わせたい場合は、`readonly`、`Readonly`、`as const`などを実際の値の型へ効かせる。`satisfies readonly T[]`だけを、値自体がreadonlyであることの表現として使用しない。
- `as const satisfies ...`は、リテラル型と変更不可性を保持しながら構造も検証する必要がある場合に限って使用する。単純な型注釈で意図を表せる場合は、より直接的な型注釈を優先する。
- TypeScriptの高度な型構文は、短く書けることを理由に採用しない。その構文を使うことで保持したい型情報や契約が明確な場合に使用する。
- 型としては等価・適合していても、構文の見た目から実際とは異なる制約を読み手が推測しやすい書き方は避ける。

## 2. 状態とデータ更新

- 同じ事実を複数のstateへ保持しない。
- 元のstateから計算できる値を別stateとして同期しない。
- 計算可能な値を同期する目的だけで`useEffect`を使わない。
- 変化しない固定値をstateへ入れない。
- props、state、入力オブジェクト、配列を直接mutationしない。
- 更新時は新しい値を作る。
- stateは、実行中に変化し、保持する必要がある値だけにする。

### 日時

- 環境依存で解釈される曖昧な日時文字列を使わない。
- コード上の固定日時は、タイムゾーンを明示したISO 8601形式にする。
- 内部計算用の日時と、人間向けの表示日時を分ける。
- 表示用に整形した文字列を、再び計算用日時として使用しない。
- この制約だけで、本番DBのタイムゾーン保存方式を決定したことにはしない。

## 3. 関数と制御フロー

- ネストを深くするより早期returnを優先する。
- 関数は、一つの判断または変換を担当する。
- 純粋関数では外部stateやDOMを変更しない。
- 値を作る関数は、外部変数の書き換えより戻り値で結果を返す。
- Boolean引数で関数の大きな動作を切り替えない。
- イベントハンドラへ複雑な変換や判断を詰め込まない。
- React componentと、Reactに依存しないデータ変換・判断処理を分ける。
- ファイル分割は行数ではなく責務で判断する。
- 将来の利用を予想した汎用化、共通化、抽象化を先取りしない。
- ドメイン上意味のある数値や文字列は、必要に応じて意味の分かる名前付き定数にする。

### 命名

- 名前だけで、何を表す値・関数・処理なのかをできるだけ判断できるようにする。
- プロジェクト固有の概念が分かっている場合は、`data`、`item`、`value`、`info`、`temp`、`result`、`obj`などの抽象的な名前だけで済ませない。汎用的な型ガードなど、本当に一般的な処理では例外とする。
- このプロジェクトでは`log`を単独の変数名、一時変数名、引数名、関数名として使わない。EmotionLogを表す場合は`emotionLog`、ログ出力器なら`logger`、デバッグ用の文字列なら`debugMessage`、監査記録なら`auditLogEntry`のように、対象と役割が一意に近くなる名前を使う。`operationLog`のように『何の操作・何の記録か』をさらに解釈する必要がある名前は避ける。
- コレクション名も対象を明示する。例えば`logs`ではなく`emotionLogs`、固定検証データなら`fixedEmotionLogs`のようにする。
- 関数名は、可能な限り「何をするか」と「何を対象にするか」が分かる動詞を含める。`processData`や`handleValue`のように対象や結果が曖昧な名前を避ける。
- 外部ライブラリ境界では、ライブラリ由来の値とアプリ側の値を名前でも区別する。例えば`plotlyLayout`から`visibleRange`を作るようにする。
- コールバックの引数名も省略しすぎない。例えば`FIXED_EMOTION_LOGS.map((emotionLog) => emotionLog.feltAt)`のように、要素が何か分かる名前を使う。
- 短い名前の方が一般的でも、読み手が別の意味と取り違える可能性がある場合は、具体的な名前を優先する。人間だけでなくAIが後続変更を行う場合も、同じ対象・役割として解釈できる粒度を基準にする。

### コメント

- コメントはコードの逐語的な説明ではなく、コードだけでは判断しにくい意図、前提、境界条件、例外、将来タスクとの境界を補うために使う。
- 関数名だけでは責務や戻り値の意味を十分に判断しにくい関数には、関数の直前へ短いコメントまたはJSDocを置く。特に、外部ライブラリ値の変換、型ガード、`null`を返す境界処理には、何を判定・変換し、`null`が何を意味するかを残す。
- タスク固有の仮値や検証用コードには、それが本番仕様ではないことがコードだけでは分かりにくい場合、理由をコメントで残す。
- 関数コメントがあることを理由に曖昧な関数名を許容しない。まず命名で責務を表し、コメントは命名だけでは伝わらない情報を補う。
- `xをyへ代入する`のようにコードをそのまま日本語化するコメントは書かない。
- コード変更で前提や処理が変わった場合はコメントも同時に更新し、実装と矛盾した古いコメントを残さない。

## 4. React

- render中に副作用を発生させない。
- DOM直接操作を基本手段にしない。
- Reactのpropsとcallbackによる連携を優先する。
- `useMemo`、`useCallback`、`React.memo`を根拠なく使用しない。
- importしただけで処理実行やDOM操作などの副作用が発生するモジュールを作らない。

## 5. 外部ライブラリとの境界

外部ライブラリの値は、境界で必要な値だけを検証・変換してからアプリ内部へ渡す。

```text
外部ライブラリ
  ↓
境界で必要値を検証・変換
  ↓
アプリ固有の型・名前
  ↓
アプリ内部
```

- 外部ライブラリ固有オブジェクトをアプリ内部へ広げない。
- アプリ内部ではライブラリ用語より、プロダクトやドメイン上の意味が分かる名前を優先する。
- 特定ライブラリだけに必要な細かなルールは共通制約へ無理に恒久化せず、必要なタスクで追加する。

## 6. エラー処理

- 「まだ取得されていない通常状態」と「本来成立するはずの値が壊れている異常状態」を区別する。
- 通常の条件分岐を例外処理で表現しない。
- `try/catch`を念のための広範囲な保険として配置しない。
- `try/catch`は非同期通信、解析、外部APIなど、例外が発生する境界へ限定する。
- catchしたエラーを理由なく握りつぶさない。
- `console.log`をstate管理や成果確認の代わりにしない。
- 一時的なデバッグログはPull Request完成時までに削除する。

## 7. 品質確認

- 対象プロジェクトに定義されているlint、型チェック、build、testを必要な範囲で実行する。
- 実行した検査と結果をPull Requestへ記録する。
- コードが動くことだけでなく、共通コード制約への違反がないこともレビュー対象とする。

## 例外の扱い

タスク固有制約は、原則として共通制約への追加として扱う。

共通制約から外れる必要がある場合は、必ず次を記録する。

1. どの共通制約から外れるのか
2. なぜ外れる必要があるのか
3. どこまでを例外とするのか

一度の局所的な例外だけで共通制約を変更しない。

複数のRMやタスクで同じ例外が繰り返し必要になる場合は、共通制約自体の見直し対象とする。
