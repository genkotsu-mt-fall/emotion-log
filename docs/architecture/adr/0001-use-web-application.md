# ADR-0001: MVPの初期提供形態にレスポンシブWebアプリケーションを採用する

- 状態: Accepted for MVP
- 決定日: 2026-07-25
- 最終更新日: 2026-07-27
- 対象版: Product Brief 0.1.0
- 決定範囲: クライアントの提供形態、配布経路、MVPにおける端末機能の範囲

## 変更履歴

| 日付 | 変更内容 |
| --- | --- |
| 2026-07-25 | 初版をAccepted for MVPとして決定 |
| 2026-07-27 | 決定内容を変えず、比較単位、PWA対象外機能、確認基準、再検討条件を明確化 |

## Context and Problem Statement

本プロダクトは、利用者がPC、iPhone、Androidから感情や考えを記録し、同一アカウントを通じて複数端末から同じデータを振り返れることを必要とする。

初期MVPで検証する中心仮説は次のとおりである。

- 感情や考えを低い負担で記録できるか
- 感情を外部化し、後から振り返れるか
- 時系列表示によって過去の記録を探索できるか
- 複数の記録を見比べられるか
- URLを共有するだけで、検証参加者が試用を開始できるか

この段階で優先するのは、ネイティブアプリとしての配布や端末固有機能ではなく、主要な記録・振り返り体験を早く検証し、学習結果を次の設計判断へ反映することである。

### Assumptions

- MVPでは、記録の作成と閲覧時にネットワーク接続を利用できることを前提とする
- サーバーを正本とし、同一アカウントのデータをオンラインで同期する
- 初期検証では、アプリのインストール自体をユーザー価値として評価しない
- Webで不足する要求は推測で先行実装せず、利用検証から具体的に収集する

### Out of Scope for MVP

次の機能および提供方式は、MVPの必須要件に含めない。

- App StoreまたはGoogle Playでの配布
- デスクトップ向けインストーラーによる配布
- OSウィジェット
- プッシュ通知
- 常時オフラインでの記録作成
- バックグラウンド同期
- オフラインデータとサーバーデータの競合解決
- カメラ、位置情報、ヘルスケア、センサーなどの高度な端末連携
- デスクトップOS固有の機能

## Decision Drivers

判断基準を、MVPにおける優先度順に示す。

### Must

- PC、iPhone、Androidから主要機能を利用できる
- インストールなしで試用を開始できる
- 一つのURLと配布経路で検証参加者へ提供できる
- 同一アカウントのデータを複数端末から確認できる
- アプリストア審査を経ずに修正を反映できる
- 記録・振り返りの中心仮説へ開発工数を集中できる

### Should

- タッチ操作とマウス操作の両方に対応できる
- 端末サイズに応じて表示と操作を調整できる
- 将来、必要性が確認された機能を段階的に追加できる
- ビルド、署名、ストア申請など、MVPの中心でない運用負担を抑えられる

### Not a Driver for MVP

- アプリストア上での発見可能性
- 完全なオフライン動作
- OSとの深い統合
- ネイティブUIと同等の操作感
- デスクトップOS専用機能

## Considered Options

比較単位を「MVPを利用者へどのような形態で提供するか」に統一する。

| 選択肢 | 概要 | MVP適合度 |
| --- | --- | --- |
| レスポンシブWebアプリケーション | 標準的なWeb技術で実装し、ブラウザへURLで提供する | 採用 |
| Flutterによるマルチターゲット提供 | Flutterを共通UI基盤としてWeb、モバイル、必要に応じてデスクトップへ提供する | 見送り |
| .NET MAUIによるネイティブ提供 | C#とXAMLを用いてモバイル・デスクトップ向けネイティブアプリを提供する | 見送り |
| Tauriによるインストール型提供 | Web UIを利用し、デスクトップ・モバイル向けパッケージとして提供する | 見送り |
| レスポンシブWeb＋PWA機能 | Webアプリにインストール、オフライン、通知などを段階的に追加する | MVPでは見送り |

### Option 1: レスポンシブWebアプリケーション

#### 利点

- インストールなしで利用を開始できる
- PC、iPhone、Androidへ一つのURLで提供できる
- 検証参加者や採用担当者へ共有しやすい
- アプリストア審査なしで更新を反映できる
- 配布作業よりも主要UXの実装と検証へ工数を集中できる
- 画面サイズに応じてレイアウトと操作を調整できる
- 将来、必要なPWA機能を段階的に追加できる

#### 不利益・リスク

- オフライン利用を保証できない
- ブラウザおよび端末ごとの差異を検証する必要がある
- OSウィジェット、バックグラウンド処理、センサーなどとの深い統合には制約がある
- モバイルブラウザ特有のビューポート、キーボード、タッチ、ジェスチャーの差異へ対応する必要がある

#### リスク低減策

- iPhone SafariとAndroid ChromeをMVPの必須確認対象にする
- PCでは少なくともChrome、Edge、macOS Safariで主要フローを確認する
- 横パン、ソフトウェアキーボード表示、フォーカス、スクロール競合を実機で確認する
- ブラウザ依存の不具合とWebでは満たせない要求をIssueとして記録する

### Option 2: Flutterによるマルチターゲット提供

#### 利点

- iOS、Android、Webなどを共通コードベースから対象にできる
- 独自描画、アニメーション、ジェスチャーを統一的に実装しやすい
- 必要に応じてインストール型アプリとして提供できる

#### 見送る理由

- DartとFlutter固有の開発・ビルド知識が追加で必要になる
- Webだけでなくネイティブも提供する場合、OS別のビルド、署名、配布、動作確認が増える
- iOS向けの最終ビルドと検証にはmacOS環境が必要になる
- MVPの中心ではない配布形態とプラットフォーム対応へ工数が分散する
- 現時点の主要UIは、標準的なWeb技術で検証可能である

#### 再検討条件

- オフライン利用が中心要件になる
- スマートフォン固有の操作体験や描画性能が主要価値になる
- iOS・Android向けインストール型アプリの需要が継続的に確認される
- OS機能との統合がプロダクトの主要価値になる

### Option 3: .NET MAUIによるネイティブ提供

#### 利点

- C#とXAMLを使用してAndroid、iOS、macOS、Windows向けアプリを共通化できる
- ネイティブアプリとして配布できる
- 端末機能やプラットフォームAPIへ接続できる

#### 見送る理由

- 一般的なブラウザ版を主要対象としていないため、URLだけで利用するWeb版を別途検討する必要がある
- C#、XAML、.NET MAUI固有の構成を採用する必要がある
- OS別のビルド、パッケージ、署名、配布、動作確認が増える
- 公式の主要対象はAndroid、iOS、macOS、Windowsであり、ブラウザとLinuxデスクトップを含む一つの配布経路にはならない
- MVPの主要仮説に対して、ネイティブアプリ化の追加コストを正当化する要求がまだない

#### 再検討条件

- .NET技術の採用自体が組織またはプロダクトの主要要件になる
- Windows中心のネイティブ機能が必要になる
- C#資産との統合がWeb提供より大きな価値を持つ

### Option 4: Tauriによるインストール型提供

#### 利点

- HTML、CSS、JavaScriptによるWeb UIを再利用してインストール型アプリを作成できる
- デスクトップとモバイルを対象にできる
- Rustやプラグインを通じてOS固有機能へ接続できる
- システムのWebViewを利用するため、ブラウザエンジンを同梱する方式より小さな配布物を構成できる

#### 見送る理由

- Rust、Tauri固有設定、権限設定、OS別パッケージが追加される
- OSごとのWebView差、プラグイン対応、署名、配布を確認する必要がある
- MVPの主要UIと同期要件は通常のWebアプリだけでも検証できる
- インストール型にすること自体の利用価値がまだ確認されていない

#### 再検討条件

- インストール型デスクトップアプリが明確に必要になる
- ローカルファイル、システムトレイ、グローバルショートカットなどのOS機能が主要要件になる
- Web UI資産を維持したままネイティブ機能を追加する必要が生じる

### Option 5: レスポンシブWeb＋PWA機能

PWAはWebアプリと排他的な実装方式ではなく、Webアプリへインストール可能性、オフライン動作、キャッシュ、通知などを段階的に追加する構成である。

#### 利点

- WebのURL配布を維持しながら、ホーム画面やランチャーから起動できる
- Service Workerとキャッシュ戦略により、一部のオフライン利用や耐障害性を追加できる
- 対応環境では通知などの機能を追加できる

#### MVPで実装しないPWA関連機能

- Web App Manifestを用いたインストール体験の提供
- `display: standalone` などによるアプリ風表示
- Service Workerによるアプリシェルやデータのオフラインキャッシュ
- オフライン状態での記録作成
- オンライン復帰時の再同期
- 複数端末・複数編集間の競合検出と解決
- Push APIを用いたプッシュ通知
- Background Syncなどを用いたバックグラウンド処理

通常のfavicon、標準的なWebメタデータ、HTTPキャッシュは、この除外範囲に含めない。

#### 見送る理由

- オフライン作成を認めると、ローカル保存、再送、重複、順序、競合解決の設計が必要になる
- Service Workerのライフサイクルとキャッシュ更新戦略が追加される
- ブラウザとOSによってインストール・通知・バックグラウンド機能の対応差がある
- 初期仮説の検証に必須ではない

#### 再検討条件

- ホーム画面やランチャーから素早く起動したい需要が、利用検証で継続的に確認される
- 通信できない状況での記録需要が確認される
- 通知が継続利用や主要ユースケースに必要だと確認される
- オフライン同期と競合解決へ投資する価値を説明できる

## Decision Outcome

MVPの初期提供形態として、PC、iPhone、Androidのブラウザで利用できるレスポンシブWebアプリケーションを採用する。

提供は一つの公開URLを基本とし、アプリストアおよびインストーラーによる配布は行わない。

MVPでは、Web App Manifestによるインストール対応、Service Workerによるオフライン対応、プッシュ通知、バックグラウンド同期などのPWA関連機能を実装しない。

オンライン接続を前提として、サーバー上の同一アカウントデータを複数端末から利用できる構成を採用する。

## Rationale

レスポンシブWebアプリケーションは、MVPで最優先する次の条件を、最小の配布・運用負担で同時に満たす。

- 複数種類の端末から利用できる
- URLだけで試用を開始できる
- 変更を迅速に公開できる
- 主要な記録・振り返り体験へ開発工数を集中できる

Flutter、.NET MAUI、TauriおよびPWA機能は、それぞれ有効な選択肢である。しかし、それらが強みを持つインストール、オフライン、OS統合、ネイティブ操作などは、現時点ではMVPの中心仮説ではない。

したがって、必要性が確認されていない機能のために配布経路、技術スタック、同期設計、テスト対象を増やすより、Webで主要仮説を検証し、具体的な不足要求が得られた時点で再選定する方針を採用する。

## Consequences

### Positive

- 一つの公開URLで複数端末から試せる
- 検証参加者への案内と利用開始が単純になる
- 改修をアプリストア審査なしで迅速に配布できる
- 初期MVPの技術範囲と運用範囲を抑えられる
- 記録、振り返り、探索、比較という主要UXの検証へ集中できる
- Webで十分か、ネイティブまたはPWAが必要かを実際の要求から判断できる

### Negative

- オフラインでの記録作成と閲覧を保証しない
- アプリストアから配布しないため、ストア経由の発見性を得られない
- OSウィジェット、通知、バックグラウンド処理、センサーなどの深い端末連携を利用しにくい
- ブラウザ、OS、画面サイズ、入力方式ごとの差異を検証する必要がある
- モバイルSafariでは、ビューポート、ソフトウェアキーボード、タッチ、スクロールなどを重点的に確認する必要がある
- 将来ネイティブ化する場合、一部のUIまたはクライアント実装を再設計する可能性がある

## Confirmation and Verification

実装が本ADRに従っていることを、次の条件で確認する。

### Architecture Compliance

- 主要機能が、アプリのインストールなしでHTTPSの公開URLから利用できる
- App Store、Google Play、デスクトップインストーラーをMVPの必須配布経路にしていない
- Service Worker、Push API、Background Syncを主要機能の成立条件にしていない
- オフライン作成と競合解決をMVPの機能として提供していない
- クライアント側にだけ存在する未同期データを正本として扱わない

### Functional Verification

最低限、次の実機または実ブラウザ確認を行う。

- PCの対象ブラウザで、ログイン、記録作成、時系列閲覧、比較が完了できる
- iPhone Safariで、ログイン、入力、保存、縦スクロール、横パンが完了できる
- Android Chromeで、ログイン、入力、保存、縦スクロール、横パンが完了できる
- URLを開くことで試用を開始できる
- 同一アカウントの記録を複数端末から確認できる
- 端末幅が変わっても、主要操作が画面外へ失われない
- ソフトウェアキーボード表示中も、入力対象と保存操作へ到達できる

## Product Validation

技術的に動作することとは別に、Webという提供形態がMVPの目的に適しているかを、利用検証で確認する。

- 検証参加者が、追加のインストール説明なしで利用を開始できる
- ブラウザ利用が記録開始の重大な障壁になっていない
- iPhone、Android、PCのいずれでも、主要タスクの完了を妨げる問題がない
- オフライン、通知、ホーム画面起動、OS統合を求める要求を、発生件数とユースケースを含めて記録できる
- Webで満たせない要求が発生した場合、要求、対象利用者、頻度、影響、代替策をIssueまたは新しいADRの入力として残せる

## Reconsideration Triggers

次のいずれかが確認された場合、本ADRの前提を再評価し、新しいADRを作成する。

- ネットワーク接続なしでの記録が主要ユースケースになる
- オフライン中の編集と、複数端末間の同期・競合解決が必要になる
- プッシュ通知またはバックグラウンド処理が主要価値になる
- App StoreまたはGoogle Playでの配布が獲得、信頼、課金、組織要件のために必要になる
- カメラ、位置情報、ヘルスケア、センサー、ウィジェットなどとの深い統合が主要価値になる
- ブラウザ制約により、主要タスクのユーザビリティまたは性能要件を満たせない
- デスクトップ向けローカルファイル連携やOS統合が主要要件になる
- Web、Flutter、.NET MAUI、Tauriなどを比較し直すだけの具体的な要求と検証結果が得られる

本ADRを置き換える場合は、ADR-0001を削除または結論だけ書き換えるのではなく、新しいADRから本ADRを `Superseded` として参照し、意思決定履歴を保持する。

## Follow-up Work

- 対象ブラウザと端末のサポート方針をテスト計画に定義する
- レスポンシブレイアウトとタッチ操作の受け入れ基準をUI仕様に定義する
- 複数端末同期の前提を、認証・API・データ設計の資料へ引き継ぐ
- Webで不足した要求を分類して記録できるIssueテンプレートを用意する
- オフラインまたはネイティブ化を再検討する際は、新しいADRを作成する
