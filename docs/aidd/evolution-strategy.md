# AIDDの段階的な発展方針

- 状態: Working Strategy
- 作成日: 2026-08-15

## 1. 目的

Emotion Logの開発では、リポジトリを正本として、人間とAIが同じ現在地と判断材料を参照できる状態を維持する。

現在は、利用者がChatGPTと一つずつ壁打ちしてプロダクト、設計、計画、実装方針を決めることを重視する。

このやり方で得たレビュー観点、判断方針、検証方法を少しずつ再利用可能にし、モデル使用量を抑えながら、承認回数を減らし、最終的には複数のエージェントが並列で開発できる状態へ進める。

AIDDそのものを作ることを目的にせず、Emotion Logを作る過程から必要な仕組みを育てる。

## 2. 現在の前提

- GitHubリポジトリ内の文書を正本とする。
- `docs/state.md`は、マージ済みの現在地と明示的なcheckpointだけを表す。
- 現在の作業フローの正本は`docs/skills/000-workflow.md`とする。
- 現在はHuman-led AIDDを基本とし、プロダクト判断をエージェントへ先に委譲しない。
- Codexなどのモデル使用量には上限がある前提で、モデルでなくても実行できる処理にはモデルを使わない。
- 実行環境をWindows、WSL、特定のローカルパスへ固定する長期ルールは作らない。

## 3. 基本原則

### 3.1 一度決めたことを繰り返し推論させない

人間とAIで確定した判断が今後も必要なら、適切な正本文書へ残す。

同じ判断を毎回プロンプトで説明する状態を減らす。

### 3.2 判断と機械処理を分ける

意味の判断が必要な処理は、人間、ChatGPT、Codexなどが担当する。

結果が決まっている処理は、可能ならscript、lint、test、CIなどへ移す。

例:

- 設計上どの責務に置くか判断する: AIまたは人間
- `git diff --check`を実行する: 機械処理
- 同じ入力に対する境界条件を検証する: test
- UXの意味を変えてよいか判断する: 人間

### 3.3 必要な文書だけ読む

エージェントが毎回リポジトリ全体を探索しなくてよい構造を維持する。

基本経路は次とする。

`AGENTS.md`
→ `docs/state.md`
→ `docs/skills/000-workflow.md`
→ `current.path`
→ 必要な関連文書

### 3.4 自動化の価値はフェーズごとに判断する

将来も残る自動化だけを優先しない。

自動化候補を次の3種類で見る。

- A. 今のフェーズを安くするもの
- B. 次のフェーズへ進むために必要なもの
- C. 長期的に使い続けるもの

暫定自動化でも、現在のフェーズ中に作成・保守コストを十分回収できるなら採用してよい。

利用頻度が下がった暫定自動化は、無理に長期保守しない。

### 3.5 自律度は実績を見て上げる

エージェントへ任せる範囲は、機能が存在するから広げるのではなく、低リスクな実タスクで意図した結果を再現できた実績を見て広げる。

レビュー修正が繰り返し必要な間は、その判断を先に文書、Skill、testなどへ戻す。

## 4. 3つのレーン

AIDDの改善を次の3レーンで捉える。

### Decision Lane

利用者とChatGPTを中心に、何を作るか、何を今決めるか、何を後へ送るかを決める。

現在はここを最も重視する。

### Execution Lane

確定した内容を、手動操作、script、Codex、GitHub Copilotなどで実現する。

判断済みで範囲が小さく、検証条件が明確な作業ほどエージェントへ委任しやすい。

### Learning Lane

壁打ちやPull Requestレビューで得た修正理由を、次回から再利用できる形へ戻す。

レビュー指摘は原則として次のように分類する。

- 今回だけの判断: Task、ADR、OQ、要件などへ残す。
- 今後も繰り返す判断: レビュー観点と判断方針、共通ルール、Skillなどの候補とする。
- 機械的に判定できるもの: script、lint、test、CIなどの候補とする。

## 5. 発展フェーズ

### Phase 1: Human-led AIDD

現在の基本フェーズ。

流れ:

GitHub
→ ChatGPTで正本を確認
→ 利用者と壁打ち
→ ChatGPTが変更内容または変更ファイルを作成
→ ローカル環境へ反映
→ 必要な手動確認
→ Pull Request
→ レビュー
→ merge

このフェーズでは、利用者自身のレビュー観点と判断方針を集めることを優先する。

追加する仕組みは小さくする。

- `AGENTS.md`を共通入口として使う。
- 同じレビュー判断が繰り返されたら、共通化する価値を確認する。
- 同じ手操作が繰り返されたら、暫定helperやscriptの費用対効果を確認する。
- lint、build、test、文書整合性確認など、機械判定できる検証を少しずつ固定する。

ZIPのダウンロード、WSLへの反映など、将来は不要になる可能性がある処理でも、このフェーズで繰り返し発生し、作成コストを回収できるなら暫定自動化してよい。

### Phase 2: Single-agent Pilot

プロダクト判断を含まない小さなタスクから、一つのエージェントへ試験委任する。

委任候補は次を満たすことを目指す。

- 目的と対象外が明確。
- 重要な判断が確定済み。
- 変更範囲を予測できる。
- 完了条件を確認できる。
- 自動検証または明確な手動検証がある。
- 新しい判断が必要になった場合の停止条件が分かる。

基本の人間承認点は、仕様確定とPull Requestレビューへ寄せる。

エージェント利用後は、修正回数だけでなく、なぜ修正が必要だったかをLearning Laneへ戻す。

### Phase 3: Agent Execution

Agent-readyなタスクについて、仕様確定後の実装途中では人間の介入を減らす。

流れ:

確定したTaskまたはIssue
→ Agent
→ 変更
→ script / test / CI
→ Pull Request
→ 意味のレビュー

この段階では、Git操作や検証commandなど、判断不要な反復処理へモデル使用量を使わない構成を強める。

### Phase 4: Parallel Execution

依存関係が分離できるAgent-readyタスクを複数エージェントへ並列委任する。

`docs/state.md`を複数エージェントの実行キューへ変えない。

- `docs/state.md`: 人間が現在どの判断やロードマップを進めているかを表す。
- GitHub Issuesなど: 実行可能になったエージェント向けタスクのキューとして使う。

並列化前に、変更範囲の衝突、依存関係、自動検証、merge順序を扱える状態にする。

### Phase 5: Multi-agent Autonomous

低リスクで検証可能なタスクは、複数エージェントが継続的に実行できる状態を目指す。

すべてを無条件に自動mergeすることは目標にしない。

人間承認を残す例:

- データモデルや公開APIの意味変更
- 認証、認可、個人データの扱い
- 利用者体験の意味変更
- ロードマップやMVP範囲の変更
- 後から戻しにくい外部契約や本番変更

自律度はリスクと再現実績に応じて変える。

## 6. エージェント向け文書の育て方

### `AGENTS.md`

ツール横断の共通入口として短く保つ。

詳細ルールの正本を複製せず、必要な文書へ案内する。

### レビュー観点と判断方針

今後、同じレビュー判断が複数回現れた時点で、独立文書として作成を検討する。

これは一般的な唯一の正解を定義する文書ではない。

Emotion Logで利用者が採用してきた判断の傾向と、今後も繰り返し使いたい観点を記録する。

既存のTask、ADR、OQ、`docs/skills/000-workflow.md`、`docs/engineering/code-constraints.md`と重複させない。

### `.github/copilot-instructions.md`

現時点では必須としない。

GitHub Copilot固有の繰り返し指示が実際に必要になった時点で、`AGENTS.md`や正本文書を参照する薄いadapterとして追加する。

共通ルールを複製しない。

### Skill

同じ複雑な作業手順を繰り返し、単なる文書参照だけでは不足するようになった時点で作成を検討する。

Skillの目的は大量の知識を複製することではなく、必要な正本と決定論的な処理を組み合わせ、エージェントが毎回考え直す範囲を狭めることとする。

## 7. モデル使用量の扱い

モデル利用量を開発速度の唯一の上限にしない。

作業は概ね次へ分ける。

- プロダクトや設計の意味判断: 人間 + ChatGPT、必要に応じてCodex
- 判断済みの実装: 効果が見込める範囲でCodexやCopilot
- 機械的な検証と定型処理: script、test、CI、通常のCLI

エージェントへ渡す前に、現在地、参照文書、対象外、完了条件を絞る。

モデルにリポジトリ全体の再探索や、確定済み判断の再推論を繰り返させない。

## 8. この方針の更新

この文書は将来像を固定する契約ではない。

Emotion Logの開発とAIDD運用の実績を見て更新する。

特に次を観察する。

- 人間の承認が何回必要だったか
- エージェントのPull Requestにどの修正が必要だったか
- 同じ指摘が繰り返されたか
- モデルを使わず自動化できる作業が増えたか
- 暫定自動化の利用頻度が下がったか
- 並列化しても変更同士が安全に統合できるか

自律化のために開発を止めて大規模な基盤を先に作らず、現在の開発で実際に発生した摩擦から改善する。
