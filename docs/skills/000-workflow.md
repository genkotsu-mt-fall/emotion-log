# AIDDワークフロー

## 目的

リポジトリを正本として、企画、要件、ADR、ロードマップ、タスク、実装、リリースを同じ流れで進める。

このワークフローで一つずつにするのは、**次に扱う作業対象**である。

選んだ作業対象に対するユーザーの指摘は、一度に何件でもまとめて扱う。一つの指摘ごとに議論やinstructionを分割しない。

## 入口

ユーザーは原則として次のように依頼する。

```text
リポジトリを確認して、次に何をすればいい？
```

ChatGPTは最初に`docs/state.md`を読み、その後に必要な文書だけを確認する。

## 1. 作業対象を一つ選ぶ

未完了の成果、依存関係、未決定事項、Blockerを確認し、次に扱う作業対象を一つだけ選ぶ。

作業対象は、一つの指摘ではなく、一緒に完成させる成果物または判断とする。

例:

- MVP全体計画を固める
- 一つの要件を確定する
- 一つのADRを決める
- 一つのロードマップをタスク分解する
- 一つのタスクの実装方針を固める
- 一つのPull Requestをレビューする

最初の応答では、現在地、選んだ作業対象、選定理由、たたき台を示し、フィードバックを求める。

この段階ではCopilot向けinstructionを作らない。

## 2. 普通のチャットとして議論する

同じ作業対象について、ユーザーが複数の指摘をした場合は、すべてを同じ応答で扱う。

1. 指摘をすべて拾う
2. 重複、依存、矛盾を整理する
3. 反映できる内容をすべて反映する
4. 成果物全体の更新版を提示する
5. 必要な確認があればまとめて質問する

禁止事項:

- 指摘を一件ずつ別セッションにする
- 一部だけ反映して残りを無視する
- 毎回一問だけに制限する
- 議論途中でCopilot向けinstructionを作る
- ChatGPTの提案をユーザー決定として扱う

別の成果物として独立させるべき内容は`後で扱う候補`へ置く。ただし、現在の議論を細切れにしない。

## 3. 議論を閉じてinstructionを作る

ユーザーが次のように明示した場合だけ議論を閉じる。

- 「これで決定」
- 「この内容で進める」
- 「議論終了」
- 「Copilot向け指示書を作って」

終了時は次を出す。

1. 確定内容
2. 保留・対象外
3. 最終成果物
4. GitHub Copilot Webへ貼り付ける一つのinstruction
5. Copilot実行後に共有してもらうPull Request

instructionには、議論中に承認されたすべての指摘をまとめる。

同じ結論から必要になるADR、要件、UX、OQ、ロードマップ、タスク、CHANGELOG、`docs/state.md`の変更も一つへまとめる。

instructionには、目的、確定内容、参照ファイル、作成・更新・削除、変更内容、対象外、検査、完了報告を含める。

Copilotへ新しい判断をさせない。`main`へ直接変更せず、ブランチとPull Requestを作らせる。

## 4. Pull Requestをレビューする

Pull Requestが提示されたら、instruction、差分、関連文書をまとめて確認する。

主な確認項目:

- 承認済み内容がすべて反映されている
- 複数の指摘に反映漏れがない
- 指定外の意味変更がない
- 関連文書が矛盾していない
- `docs/state.md`がマージ後の状態を示している
- テスト、lint、リンク、Markdownが正常である

結果は次のどちらかにする。

- `Accepted`: マージ可能
- `Changes required`: 修正が必要

修正が必要な場合は、見つかった修正事項をすべてまとめた一つの修正instructionを作る。

## 中断して後日再開する

議論途中で保存したい場合、ユーザーは次のように依頼する。

```text
中断して、現在地を保存する指示書を作って。
```

ChatGPTは、次を保存するcheckpoint instructionを作る。

- `docs/discussions/current.md`: 確認済み事実、暫定案、ユーザー指摘、未解決点
- `docs/state.md`: 作業対象とcheckpointへの参照

再開時はcheckpointを読み、同じ作業対象の議論を続ける。議論終了時のinstructionでcheckpointを削除する。

## stateの原則

`docs/state.md`は、マージ済みの現在地と、明示的に保存した中断状態だけを表す。

チャット中の未保存案を、決定済み・適用済みとして扱わない。

Pull Request内のstateは、そのPull Requestがマージされた後の状態を書く。

## 次の作業を選ぶ優先順位

1. checkpointがあれば再開する
2. ユーザーがPull Requestを提示したらレビューする
3. Blockerがあれば解消作業を選ぶ
4. 進行中のロードマップまたはタスクがあれば続ける
5. なければMVP到達に最も先行する成果物を一つ選ぶ
